# Secure DB Manager
Проект информационной системы для процесса Автоматизированного тестирования ПО

В проекте делается упор на использование встроенных в СУБД механизмов безопасности, в частности используются роли PostgreSQL для каждого пользователя. Когда пользователь входит в систему, создается новое подключение под его ролью. Жертвуем производительностью в пользу безопасности.

В базе данных есть несколько базовых ролей (контейнеров привилегий на представления) например `db_tester`, от них наследуются роли для каждого конкретного пользователя например `ivan_ivanov`.

## Воркфлоу

Примерная последовательность функционирования приложения:
```mermaid
sequenceDiagram
    actor User as Пользователь
    participant App as Приложение
    participant PG as Ядро СУБД (Postgres)
    participant DB as БД (Таблицы + Views)

    %% === РЕГИСТРАЦИЯ ===
    rect rgb(230, 240, 255)
        Note over User,DB: Регистрация нового сотрудника
        User->>App: Регистрация (логин, пароль, роль)
        App->>PG: Подключение (postgres)
        PG->>DB: INSERT INTO Users, UserRoles
        DB-->>PG: OK
        PG->>PG: CREATE USER ivan_ivanov WITH PASSWORD '***'
        PG->>PG: GRANT db_tester TO ivan_ivanov
        PG-->>App: Пользователь создан
        App-->>User: Успешно зарегистрирован
    end

    %% === АВТОРИЗАЦИЯ ===
    rect rgb(240, 255, 240)
        Note over User,DB: Авторизация существующего пользователя
        User->>App: Логин + пароль
        App->>PG: Попытка подключения (ivan_ivanov + пароль)
        PG->>PG: Проверка аутентификации
        alt Пароль верный
            PG-->>App: Соединение установлено (CURRENT_USER = ivan_ivanov)
            App->>App: Сохранить соединение в сессии
            App-->>User: Вход выполнен
        else Пароль неверный
            PG--xApp: Ошибка авторизации
            App-->>User: Доступ запрещен
        end
    end

    %% === РАБОТА С ДАННЫМИ ===
    rect rgb(255, 245, 230)
        Note over User,DB: Работа с данными (RLS + RBAC)
        User->>App: Запрос: показать мои тест-кейсы
        App->>PG: SELECT * FROM v_tester_assigned_cases<br/>(от имени ivan_ivanov)
        PG->>PG: 1. Проверка GRANT (входит ли в db_tester?)
        PG->>DB: 2. Запрос к View с фильтром<br/>WHERE username = CURRENT_USER
        DB-->>PG: Только строки Ивана
        PG-->>App: Результат (RLS применен)
        App-->>User: Вот твои 5 кейсов
    end

    %% === ПОПЫТКА НАРУШЕНИЯ ===
    rect rgb(255, 230, 230)
        Note over User,DB: Попытка доступа к чужим данным
        User->>App: Попытка изменить чужой тест-план
        App->>PG: UPDATE v_public_test_plans WHERE id=999<br/>(от имени ivan_ivanov)
        PG->>PG: Проверка GRANT на UPDATE
        PG--xApp: ERROR: permission denied<br/>(у db_tester нет права UPDATE)
        App-->>User: Доступ запрещен
    end
```

### Коротко

При создании пользователя нужно:
1. Проверить наличие такого имени пользователя в таблице Users
2. Создать в Users запись с именем и хешем пароля
3. Создать роль в БД на основе базовой роли Guest (менять роль будет администратор БД, только он имеет доступ к нужному представлению и привилегиям)
4. Вернуть результат: Успешно (опционально перейти на домашнюю страницу)

При авторизации:
1. Проверить успешность аутентификации
2. Создать подключение к БД на уровне приложения и сохранить его в памяти совместно с токеном сессии
3. Вернуть успешность результата и перейти на домашнюю страницу

При работе с данными:
1. По JWT токену получить нужно соединение с БД
2. Использовать представления для запросов
3. Во фронт будут возвращаться таблицы произвольной размерности
